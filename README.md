# PR Review Bot (локальный)

Поллер следит за открытыми PR в базовую ветку в одном или нескольких репозиториях,
при новых коммитах запускает
`pr-agent` (`describe` → саммари в описание PR, `review` → ревью-комментарий,
опционально `improve` → предложения по улучшению кода)
через локальную LLM **gpt-oss-20b** в **Ollama**. Всё крутится на одной машине,
наружу уходят только запросы к GitHub API.

## Установка (один раз)

### 1. Ollama + модель

1. Поставить Ollama: https://ollama.com/download (Windows — ставится как сервис).
2. Скачать модель (~13 ГБ):
   ```
   ollama pull gpt-oss:20b
   ```
3. Чтобы модель не выгружалась из VRAM между PR (холодная загрузка — десятки секунд),
   задать переменную окружения **для системы** и перезапустить Ollama:
   ```
   OLLAMA_KEEP_ALIVE=2h
   ```
4. Проверка: `ollama run gpt-oss:20b "привет"` — должен ответить.

### 2. pr-agent

Нужен Python 3.10+:
```
pip install pr-agent
```
Проверка: `python -m pr_agent.cli --help`

### 3. Конфиг в целевом репозитории

Переименовать `pr_agent.toml.example` → `.pr_agent.toml` и **закоммитить в корень
каждого целевого репозитория** (в его базовую ветку). pr-agent подтягивает его из репо сам —
там модель, русский язык ответов и исключения (картинки, бинарники, лок-файлы).

### 3a. Локальные переопределения (без коммитов в репо)

Рядом с поллером лежит `pr_agent.local.toml`. Всё, что в нём написано, **перекрывает**
`.pr_agent.toml` из репозитория — pr-agent применяет CLI-аргументы после репозиторного
файла, и поллер передаёт каждый ключ локального файла как `--section.key=value`.
Удобно крутить модель, таймауты и инструкции, не гоняя правки через PR.

Формат — подмножество TOML: `[секции]` и вложенные `[секция."под-секция"]`, строки в кавычках,
числа, `true/false`, массивы (можно многострочные), комментарии `#`. Секция с вложенными
под-секциями передаётся pr-agent целиком одним аргументом. Многострочные строки `"""..."""` не поддерживаются.
Ключи из репо, которых нет в локальном файле, остаются как есть. Файл читается при старте
поллера — после правки его нужно перезапустить.

Что применилось, видно в логе при старте (`Локальные переопределения pr-agent ...`)
и в логе pr-agent (`Updated setting CONFIG.MODEL to: ...`).

Списки (`fallback_models`, `ignore.glob` и т.п.) передаются парой `--key=@del` + `--key=[...]`:
Dynaconf 3.3 в pr-agent до середины сентября 2026 при переопределении **дописывал** список
к репозиторному, а не заменял. Пара `@del` + значение работает на любой версии.

Успех прогона поллер определяет не только по коду выхода (старые версии pr-agent при
ошибке печатают help и выходят с 0), но и по маркерам в логе (`Failed to process the command`,
`Failed to generate prediction with any model`, `Traceback` и т.д.). Если команда упала,
следующие по списку в этом цикле не запускаются.

### 4. Настройка бота

```
copy .env.example .env
```
Заполнить в `.env`:
- `GITHUB_TOKEN` — personal access token (classic) со scope `repo`; один токен на все
  репозитории, у него должен быть доступ к каждому из них
- `REPOS` — список репозиториев через запятую, например
  `myorg/frontend, myorg/backend:develop, myorg/admin`. Суффикс `:ветка` задаёт базовую
  ветку для конкретного репо; без него берётся `BASE_BRANCH`

- `PR_AGENT_COMMANDS` — какие команды pr-agent гонять для каждого PR и в каком порядке,
  по умолчанию `describe,review`. Чтобы получать ещё и предложения по улучшению кода:
  `describe,review,improve`. `improve` — это дополнительно 1–3 запроса к модели на PR
  (по чанкам диффа), так что на локальной модели PR обрабатывается заметно дольше.

Старый вариант с одной переменной `REPO=owner/repo` тоже продолжает работать.

## Запуск

```
npm start
```
(или просто `node poller.mjs`). Файлы: `poller.mjs` — поллер, `weekly-summary.mjs` — дайджест,
`pr-agent.mjs` — запуск pr-agent с локальным конфигом, `common.mjs` — общий код
(.env, список репозиториев, GitHub API).

Логика цикла (каждые `POLL_MINUTES` минут), для каждого репозитория из `REPOS` по очереди:
1. GitHub API: список открытых PR в базовую ветку этого репо.
2. Сравнение head SHA каждого PR с `state.json` (состояние хранится отдельно по репо:
   `{ "owner/repo": { "<номер PR>": "<sha>" } }`).
3. Для новых/обновлённых PR — команды из `PR_AGENT_COMMANDS` по очереди
   (одна GPU — один запрос за раз, репозитории тоже обрабатываются последовательно).
   На первой упавшей команде цепочка останавливается.
4. SHA сохраняется только если все команды прошли; иначе повтор в следующем цикле.
5. Записи закрытых PR чистятся из `state.json`; если репо убрали из `REPOS` — его
   состояние удаляется.

Если GitHub API отвалился для одного репо, остальные всё равно обрабатываются.
`state.json` старого формата (от версии с одним `REPO`) подхватывается автоматически.

Ревью-комментарий у pr-agent персистентный: при новых коммитах обновляется
существующий, а не создаётся новый.

## Модель: локальная Ollama или OpenRouter

Модель для pr-agent выбирается локальным конфигом, а какой из них активен — строкой в `.env`:

| `.env` | Конфиг | Модель | Что нужно |
|---|---|---|---|
| `PR_AGENT_LOCAL_CONFIG=pr_agent.local.toml` | локальная Ollama | `gpt-oss:20b` | GPU, Ollama, `OLLAMA_CONTEXT_LENGTH` |
| `PR_AGENT_LOCAL_CONFIG=pr_agent.local.openrouter.toml` | OpenRouter | `z-ai/glm-5.3-flash` | ключ `OPENROUTER_API_KEY` |

Переключение на OpenRouter:
1. Завести ключ на https://openrouter.ai/keys, пополнить баланс и **поставить на ключ лимит
   расходов** (Credit limit) — при ваших объёмах это единицы долларов в месяц, лимит защитит
   от сюрпризов, если что-то зациклится.
2. В `.env`: `OPENROUTER_API_KEY=sk-or-...`, `PR_AGENT_LOCAL_CONFIG=pr_agent.local.openrouter.toml`,
   `SUMMARY_PROVIDER=openrouter` (дайджест тоже через облако; `SUMMARY_MODEL` можно оставить пустым).
3. Проверить одним PR вручную, не дожидаясь поллера:
   ```
   set GITHUB__USER_TOKEN=ghp_xxx
   set OPENROUTER__KEY=sk-or-xxx
   python -m pr_agent.cli --pr_url=https://github.com/owner/repo/pull/123 review --config.model=openrouter/z-ai/glm-5.3-flash --config.custom_model_max_tokens=120000
   ```
4. `npm start`. В стартовом логе должен быть `pr_agent.local.openrouter.toml`, в логе pr-agent —
   `Updated setting CONFIG.MODEL to: "openrouter/z-ai/glm-5.3-flash"`.

Ключ в toml не кладётся: поллер передаёт его pr-agent через окружение (`OPENROUTER__KEY`).
Откат на Ollama — вернуть `PR_AGENT_LOCAL_CONFIG=pr_agent.local.toml` и `SUMMARY_PROVIDER=ollama`.
Оба конфига держат одинаковые настройки ревью (язык, лейблы, рекомендация по мёржу), отличаются
только модельной частью: в OpenRouter-варианте `ai_timeout` 300 с вместо 1800, `parallel_calls`
у `improve` включён, контекст 120k. `[openrouter] reasoning_effort = "low"` — глубина рассуждений
модели; для дайджеста то же задаёт `SUMMARY_THINK`. Сменить модель — строки `model` и
`fallback_models` в конфиге (и `SUMMARY_MODEL` в `.env` для дайджеста); ориентиры по ценам и
качеству на сентябрь 2026: GLM-5.3-Flash (текущая) ≈ gpt-oss-120b по цене при Coding Index 71.5
против 21–30; Gemini 3.8 Flash ($0.75/$3.75) и GLM-5.3 ($0.56/$2.50) — на ступень выше; Claude
Sonnet 5 ($2/$10) — самый надёжный по инструкциям и русскому языку. Если важно, куда уходит код, в `[openrouter]`
есть `provider_only` — жёсткий список провайдеров (например, только с zero-data-retention).

Ориентир по цене: один прогон `describe → review → improve` — порядка 20–30k токенов на вход
и 3–5k на выход, то есть около $0.002; в логе дайджеста выводится расход токенов на каждый запрос.

## Лейблы на PR

`describe` вешает на PR лейблы по содержанию изменений. Набор задаётся в `pr_agent.local.toml`
секциями `[custom_labels."имя"]` с описанием-подсказкой для модели (сейчас: `feature`, `bug fix`,
`ui`, `refactoring`, `tests`, `dependencies`, `docs`). Имя секции = имя лейбла на GitHub,
несуществующие лейблы создаются автоматически; лейблы, поставленные людьми, не трогаются.
Отключить — `publish_labels = false` в `[pr_description]`. Отдельно `review` вешает свои
лейблы `Review effort N/5` и `Possible security concern` (`enable_review_labels_effort/security`).

## Предварительный апрув

`AUTO_APPROVE=true` в `.env`: после `review` поллер читает комментарий ревью и, если там
«No major issues detected», «No security concerns identified», рекомендация `Safe to merge`
(включена `require_merge_recommendation` в локальном конфиге) и оценка усилий не выше
`AUTO_APPROVE_MAX_EFFORT`, ставит approve с пометкой «Предварительный апрув от бота».
Если следующее ревью (новые коммиты) находит проблемы — бот сам снимает свой approve.
На один и тот же коммит повторно не апрувит. `improve` на решение не влияет.

Важно:
- GitHub не позволяет апрувить собственный PR — PR автора токена бот пропустит. Чтобы апрув
  работал для всех, заведи отдельный bot-аккаунт с доступом к репозиториям и выдай токен ему
  (тогда и комментарии ревью будут от бота, а не от тебя).
- Если в branch protection стоит «1 approval required», апрув бота его закроет — это уже не
  «предварительно». В таком случае лучше требовать 2 approvals или ревью от CODEOWNERS.

## Недельный релиз-дайджест для бизнеса

`weekly-summary.mjs` берёт все PR, смердженные в базовую ветку каждого репозитория за
период, и просит модель описать изменения языком, понятным менеджерам: «Что нового»,
«Что исправлено», «Улучшения и прочее» — без файлов, функций и номеров PR. В конце файла
свёрнутый список PR со ссылками, чтобы при необходимости было куда провалиться.
Модели скармливаются заголовки и описания PR (включая саммари от `describe`), дифф не нужен.

Порядок работы: сначала по каждому репозиторию собирается список смердженных PR, затем
проверяется, есть ли у каждого саммари от `describe` (по заголовкам pr-agent в описании PR).
Для PR без саммари запускается **только `describe`** — описание на GitHub дополняется, тело
перечитывается. И только когда саммари есть у всех PR, модель пишет общий дайджест и файл
записывается. Если для какого-то PR саммари получить не удалось, отчёт не создаётся: поллер
повторит попытку в следующем цикле, а после `WEEKLY_SUMMARY_MAX_ATTEMPTS` (по умолчанию 3)
соберёт дайджест как есть, пометив такие PR в списке как «без саммари».

Результат — папка на период внутри `RELEASE_NOTES_DIR` (по умолчанию `release-notes/`):
```
release-notes/2026-09-07_2026-09-13/
  summary.md      # общий: «🌟 Главное за неделю» по всем проектам + разделы по каждому + список PR
  LazarReact.md   # отдельный дайджест по репозиторию + его список PR
  LazarCart.md
  Lazar.md
```
Тон — живой, с эмодзи: заголовки «✨ Что нового», «🐞 Что исправлено», «🚀 Улучшения и прочее»,
каждый пункт начинается с подходящего эмодзи. Блок «Главное за неделю» — отдельный короткий
запрос к модели поверх готовых дайджестов, появляется, если изменения были больше чем в одном
проекте. Папка не в `.gitignore` — это и есть история.

**Автоматически:** поллер сам запускает дайджест раз в неделю за прошлую полную неделю
(пн–вс) — в день `WEEKLY_SUMMARY_DAY` (1 = пн … 7 = вс) после часа `WEEKLY_SUMMARY_HOUR`.
Факт запуска хранится в `state.json` → `_meta.lastWeeklySummary`; если в назначенный день
бот был выключен, дайджест соберётся при первом тике позже на той же неделе. Отключить —
`WEEKLY_SUMMARY=false`.

**Вручную** (для тестов или за произвольный период):
```
npm run summary                                      # прошлая полная неделя
node weekly-summary.mjs --days 7                     # последние 7 дней
node weekly-summary.mjs --from 2026-09-01 --to 2026-09-14
node weekly-summary.mjs --repo xGum/LazarReact       # один репозиторий
node weekly-summary.mjs --dry-run                    # показать, у кого нет саммари, и промпт; describe и модель не звать
node weekly-summary.mjs --allow-missing              # не требовать саммари у всех PR
node weekly-summary.mjs --no-describe                # не догенерировать саммари вообще (подразумевает --allow-missing)
```
Первый прогон за старый период может занять время: `describe` для каждого PR без саммари —
это отдельный запрос к модели (1–2 минуты на gpt-oss), и он **редактирует описания уже
смердженных PR** на GitHub (описание автора сохраняется в блоке «User description»).
Если это нежелательно — `--no-describe`.

Ручной запуск не мешает поллеру: если модель занята ревью, Ollama поставит запрос в очередь.

Настройки в `.env`: `SUMMARY_MODEL` (можно взять другую модель, чем для ревью),
`SUMMARY_NUM_CTX` (контекст задаётся прямо в запросе, `OLLAMA_CONTEXT_LENGTH` тут не нужен),
`SUMMARY_THINK` (`low`/`medium`/`high` для gpt-oss — `low` быстрее и для дайджеста достаточно),
`SUMMARY_TIMEOUT_MINUTES`, `OLLAMA_URL`, `SUMMARY_PROVIDER` (`ollama` или `openrouter`, см. раздел
про модель). Тон, эмодзи и структуру текста задают `SYSTEM_PROMPT`
(дайджест по репозиторию) и `OVERVIEW_SYSTEM_PROMPT` («Главное за неделю») в `weekly-summary.mjs`.

Планировщик задач → «При входе в систему» → запуск

перезапуск по расписанию не нужен.

## Если что-то идёт не так

- **`Empty content in model response, finish_reason: length`** — модель упёрлась в контекст
  Ollama и не успела дойти до ответа (весь бюджет ушёл на рассуждения по обрезанному промпту).
  По умолчанию у Ollama контекст 4096 токенов, а pr-agent шлёт до `custom_model_max_tokens`.
  Задать системную переменную (рядом с `OLLAMA_KEEP_ALIVE`) и перезапустить Ollama:
  ```
  OLLAMA_CONTEXT_LENGTH=32768
  ```
  (в приложении Ollama для Windows то же самое есть в Settings → Context length).
  Проверка: `ollama ps` после запроса показывает колонку CONTEXT; в
  `%LOCALAPPDATA%\Ollama\server.log` не должно быть `truncating input prompt`.
- **`Empty content in model response, finish_reason: stop`** — gpt-oss отдаёт ответ в канал
  рассуждений, а `content` пустой. Лечится в `pr_agent.local.toml`: `model = "ollama_chat/gpt-oss:20b"`
  (эндпоинт `/api/chat` вместо `/api/generate`) и `custom_reasoning_model = true`.
  Если не помогло — обновить Ollama и заново `ollama pull gpt-oss:20b`.
- **`Failed to generate prediction with any model`** — это обёртка, реальная причина в
  строке `WARNING ... Failed to generate prediction with ...` выше. Частый случай —
  таймаут: у pr-agent `ai_timeout` по умолчанию 120 с, в локальном конфиге стоит 1800.
- **Кривой JSON / мусор в ответах модели** — в `.pr_agent.toml` в `[config]`
  попробовать `custom_reasoning_model = true` (gpt-oss — reasoning-модель,
  иногда служебные токены протекают в вывод).
- **Не хватает VRAM / медленно на больших диффах** — снизить
  `custom_model_max_tokens` до 32768.
- **`python` не находится (Windows)** — в `.env` поставить `PYTHON_CMD=py`.
- **Прогнать PR заново** (например, после исправления конфига, если старый прогон оставил
  мусор в описании) — удалить его запись из `state.json` (`"owner/repo": { "<номер>": ... }`)
  и дождаться следующего цикла. `describe` перепишет свою часть описания, `review` обновит
  свой комментарий.
- Разовый ручной прогон для отладки:
  ```
  set GITHUB__USER_TOKEN=ghp_xxx
  python -m pr_agent.cli --pr_url=https://github.com/owner/repo/pull/123 review
  ```
